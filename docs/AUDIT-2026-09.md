# FlupCode — Auditoría de producto, capacidades, UX y arquitectura

_Fecha: 14 de septiembre de 2026 · Rama auditada: `power` @ `15196ef` (harness 1.0.18, motor OpenCode 1.18.30) · Referencias externas: OpenCode v1.18.30 (2026-09-09), Oh My ClaudeCode 5.4.0 (commit `5281b19`, 2026-09-11), Claude Code 2.1.270._

Este documento es una fotografía crítica del estado real de FlupCode y un plan de 3–6 meses para convertirlo en un coding-agent harness. Toda afirmación sobre FlupCode está verificada contra el código de `packages/harness` (y `harness-desktop`, `remote`, `relay`, `flupcode-cli`); las rutas se dan relativas a `packages/`. Cuando algo está en el motor de OpenCode pero no en la UI de FlupCode, se dice explícitamente. `docs/PARITY.md` y `docs/ROADMAP.md` **no** se han tomado como fuente de verdad: se han contrastado y, en varios puntos, contradicho.

Convención de estados: **EXISTE** (funciona y se usa), **PARCIAL** (existe pero incompleto o roto en algún camino), **PLACEBO** (hay UI pero no hace nada real), **NO EXISTE**.

---

## 0. Executive Summary

**Qué es FlupCode hoy.** No es un fork profundo de OpenCode: es un cliente web nuevo (`packages/harness`, ~12.000 líneas de TS/TSX (9.500 de ellas TSX) más 5.850 de CSS, con `src/app.tsx` de 2.598 líneas concentrando estado, llamadas al motor y orquestación) que habla con `opencode serve` por HTTP/SSE. Los paquetes upstream son read-only por diseño (ADR-0001/0002), lo cual es una decisión acertada. Pero el harness **no reutiliza nada de `@opencode-ai/session-ui` ni `@opencode-ai/ui`** (están en `harness/package.json:20-21` y no hay un solo import en `src/`), así que reimplementa desde cero, y con menos alcance, el timeline, el composer, los diffs y el resaltado (un highlighter de regex de 200 líneas en `harness/src/highlight.ts` frente a Shiki + Pierre + markdown en worker en upstream). El resultado es que la app oficial de OpenCode (`packages/app`, "Desktop v2") es hoy **más capaz** que FlupCode en árbol de archivos, pestañas, renderizado de herramientas, reasoning, diffs, timeline, MCP y cola de prompts.

**El hallazgo más grave: el camino de ejecución está mal elegido.** Las sesiones de la pestaña Code envían el prompt por la API V2 (`harness/src/client.ts:184-201` → `client.v2.session.prompt`), que ejecuta el **runner V2 de `packages/core`**. Ese runner es, según su propio checklist (`core/src/session/runner/llm.ts:44-86` y `core/src/tool/builtins.ts:22-30`), una obra en curso: **no tiene task tool (subagentes), ni herramientas MCP ni de plugins, ni LSP, ni reintentos ante 429/5xx, ni detección de doom-loop, ni generación de título/resumen, ni estado durable busy/retry/idle**. La app oficial de OpenCode evita esto deliberadamente y enruta todos los prompts por el runtime legacy (`app/src/utils/server-compat.ts:200-215`). Es decir: hoy, en FlupCode, un agente **no puede delegar en subagentes ni usar MCP** en el flujo principal, aunque la UI muestre un `SubagentList` y un `McpManager`. Cambiar esto es la primera tarea del roadmap y desbloquea casi todo lo demás.

**La documentación de estado no es fiable.** `docs/ROADMAP.md` declara 63/66 tickets hechos. Verificado en código: tags de sesión (F3-8) no existen; mover sesión (F3-7) es un menú que llama a una función que siempre lanza (`client.ts:313-315`); invocar skills (F3-10) siempre lanza (`client.ts:310-312`); el MCP manager (F3-14 "bloqueado") es un panel completo sobre stubs que devuelven `[]` (`client.ts:451-457`) cuando el servidor 1.18.30 sí expone `/mcp` (`opencode/src/server/routes/instance/httpapi/groups/mcp.ts`); los editores de permisos/agentes/comandos (F3-13, F4-3) no existen (sólo un textarea JSON sobre `/config`); las rutinas (F4-6) son un `setInterval` de 30 s en la pestaña del navegador (`app.tsx:1508`); los artifacts (F4-5) son una lista de rutas de archivos tocados en la sesión actual con botón "copiar"; compartir sesión está marcado como imposible cuando el SDK vendorizado tiene `session.share/unshare`. Antes de planificar hacia delante hay que restablecer la verdad: reescribir PARITY.md contra el harness (no contra `packages/app`) y degradar esos tickets.

**Seguridad.** El modo de permisos por defecto es `auto` = `{"*": allow}` (más `external_directory: ask`) y se reescribe sobre la sesión en cada envío (`harness/src/permission-modes.ts:24-31`, `app.tsx:2014-2018`), anulando la configuración del proyecto y describiéndose en la UI como "el agente decide según sus permisos"; Electron arranca con `webSecurity:false` y `sandbox:false` (`harness-desktop/src/main/index.ts:26-29`) con un iframe de navegador sin `sandbox`; las API keys de todos los proveedores viajan en claro al navegador (y por el túnel al móvil) y se copian automáticamente a un segundo almacén sin consentimiento (`app.tsx:281-331`). Nada de esto es aceptable en un producto que además permite control remoto desde el teléfono.

**Nivel actual y nivel objetivo.** En la escala assistant → agent → harness → orchestration platform, FlupCode es hoy la UI de un agente único (nivel 2), y en el camino Code está por debajo del propio OpenCode. Para ser harness necesita algo que hoy no tiene ningún componente suyo: **una entidad de ejecución durable, observable y supervisable por encima de la Session de OpenCode** (aquí la llamo *Run*), con tareas, workflows, verificación, artefactos y checkpoints, y un proceso que la ejecute cuando el navegador no está abierto. Un harness no puede vivir sólo en el renderer; las rutinas en `setInterval` lo demuestran.

**Lo que ya tiene el motor y FlupCode no expone** (y por tanto es barato): task tool con `background` (tras flag), `subagent_depth`, comandos con `subtask`/agente/modelo, skills con permisos por agente, reglas de permisos por herramienta y patrón con `always` persistido, snapshots git para revert por mensaje, fork desde mensaje, mover sesión (control-plane), share, worktrees experimentales, `format: json_schema` (salida estructurada, ideal para gates de verificación), eventos durables con replay `after`, tokens/coste por mensaje, question tool, `/vcs/diff` estructurado, `/file/status`, `/find/symbol`, hooks de plugin (`tool.execute.before/after`, `permission.ask`, `experimental.chat.system.transform`, tools propias). FlupCode ya instala un plugin de motor (`remote/src/engine-plugins.ts`), así que el precedente para meter lógica del harness dentro del loop existe.

**Estrategia recomendada (3–6 meses), en cuatro fases:**

1. **Verdad y cimientos (semanas 1–6).** Ejecutar Code por el runtime legacy tras un `EngineAdapter`; store de mensajes dirigido por eventos (hoy cada evento SSE dispara refetch completo del transcript cada 300 ms); reconexión SSE con heartbeat y replay; seguridad por defecto corregida; adoptar `session-ui` para timeline/diff/composer (o decidir explícitamente lo contrario); eliminar placebos y cablear lo que ya existe (MCP, share, move, fork-desde-mensaje, queue/steer, reasoning, permisos guardados); documentación honesta.
2. **Primitivas del harness (semanas 7–14).** `harness-server` (SQLite propio, cron, git, orquestación) hospedado por el desktop y por `flupcode serve`; modelo Run/Task; vista de supervisión; editor de agentes; artifacts reales; checkpoints (snapshot + resumen); observabilidad (timeline de tools, tokens/coste por agente/tarea); Context Inspector.
3. **Workflows y verificación (semanas 15–20).** Workflows secuenciales declarativos (plan → implement → test → review) ejecutados por el harness con sesiones hijas, gates con salida estructurada, bucle de verificación (test/lint/typecheck con reintentos acotados), review agent con comentarios en el diff, git (commit/branch/PR), rutinas server-side.
4. **Paralelismo y routing (semanas 21–26).** Worktree por tarea, grafo de tareas con dependencias y ejecución paralela, perfiles de modelo y presupuestos, context packs y handoffs.

**Respuesta corta a las dos preguntas estratégicas.** (1) Tras la paridad, lo que hace a FlupCode una categoría distinta no es "más agentes" sino **poseer el Run**: ejecuciones durables con plan, tareas, verificación, artefactos, checkpoints y supervisión, cosa que OpenCode (runtime) no hace y que Claude Code hace de forma opaca en terminal. (2) El conjunto mínimo de primitivas nuevas es **Run/Task, Workflow, Artifact, Checkpoint, Policy (permisos + routing de modelo) y Context Pack**; **Agent, Session, Skill, Tool, Model y Permission ya existen en el motor y FlupCode debe exponerlos y editarlos, no reimplementarlos**. Agent Team no es una primitiva: es la proyección de las tareas de un Run.

## 1. Estado real de FlupCode

### 1.1 Arquitectura efectiva

```
packages/harness (SolidJS, renderer)          packages/harness-desktop (Electron main)
  app.tsx (2.598 líneas: estado + engine)       arranca/adjunta `opencode serve`, updater,
  client.ts  → SDK v2 (legacy + /api)           menú, IPC remoto, instala plugin de variantes
  transport.ts → fetch/WS o túnel E2E
       │ HTTP + SSE                                  packages/remote + relay + flupcode-cli
       ▼                                             (control remoto E2E, push, `flupcode remote`)
  opencode serve 1.18.30
    ├─ runtime legacy V1 (/session/*): tools completas, MCP, task, LSP, retries, títulos
    └─ runtime V2 (/api/session/*): core runner incompleto  ◀── FlupCode "Code" envía aquí
```

Puntos relevantes verificados:

- **Dos runtimes, mezclados.** Code usa V2 para crear sesión y prompt (`client.ts:180-201`) y legacy para fork, rename, delete, shell, command, children, diff (`client.ts:280-340`); la pestaña Chat usa legacy `promptAsync` con system prompt propio (`client.ts:208-229`, `chat.ts`). El transcript de cada sesión se obtiene fusionando **dos** listas (`/api/session/:id/message` y `/session/:id/message`) y ordenándolas (`client.ts:322-340`). Consecuencia: los mensajes V1 y V2 viven en tablas distintas y la UI depende de que la fusión sea correcta.
- **Estado por refetch, no por eventos.** Cada evento SSE `message.*`/`session.next.*` programa (debounce 300 ms) un `GET` completo de mensajes, sesiones y `git status` (`app.tsx:667-690`, `740-758`). Los deltas de texto se acumulan sólo para la sesión seleccionada en `liveText` y se descartan cuando el refetch los contiene (`app.tsx:723-727`, `863-881`). El `<For>` del timeline se re-crea entero en cada refetch porque las referencias cambian (`SessionView.tsx:712`), perdiendo el estado abierto/cerrado de los grupos de tools.
- **Persistencia cliente = localStorage** (37 claves, `storage.ts:18-55`): pins, stash, historial de prompts, rutinas, layout, modelo, modo de permisos. Sin IndexedDB, sin caché de transcripts entre recargas.
- **Renderizado propio**: `marked` + DOMPurify síncrono por token (`Markdown.tsx:30`), highlighter regex (`highlight.ts`), diff LCS O(n·m) en hilo principal (`highlight.ts:87-96`, `SessionView.tsx:106-136`). Reasoning descartado del transcript (`SessionView.tsx:416`).
- **Lista de sesiones limitada a 200 sin paginación** (`client.ts:174`).
- **Tests**: 6 ficheros de funciones puras + Playwright smoke/remote; sin cobertura de `app.tsx`, del cliente ni del SSE.

## 2. Los 20 gaps más importantes

Ordenados por daño actual × valor de resolverlos. Categoría entre corchetes según la taxonomía A–J del brief.

1. **[G/A] El camino Code ejecuta en el runner V2 incompleto** → sin subagentes, MCP, LSP, reintentos, doom-loop, títulos. Fix: prompt legacy (`promptAsync`) tras un `EngineAdapter` como hace `app/src/utils/server-compat.ts`.
2. **[H/G] Estado por refetch** (`app.tsx:667-690`): transcript entero ×2 requests cada 300 ms durante un turno, `git status` por evento, grupos de tools que se colapsan solos, texto que salta entre `liveText` y el mensaje refetcheado. Fix: `createStore` por id + reductor de eventos `session.next.*`/`message.part.*` + `reconcile`.
3. **[G] SSE sin heartbeat ni replay** (`client.ts:24-58`): un socket medio abierto cuelga para siempre con el pill en "Connected"; tras reconectar no se refrescan permisos/preguntas → agente bloqueado invisible (`app.tsx:761-769`).
4. **[Seguridad/I] Modo `auto` = allow-all por defecto (salvo `external_directory: ask`)**, reescrito sobre la sesión en cada envío, con descripción engañosa en la UI (`permission-modes.ts:24-31`, `ModeMenu.tsx:48`).
5. **[Seguridad] Electron sin SOP ni sandbox + iframe sin sandbox + motor local sin contraseña** (`harness-desktop/src/main/index.ts:26-29`, `WorkspacePanels.tsx:56`).
6. **[Seguridad] API keys en claro al renderer y al móvil, auto-copiadas** (`app.tsx:281-331`).
7. **[A] MCP inexistente en la práctica** (stubs) cuando `/mcp` está vivo en el servidor.
8. **[A] Skills no invocables; comandos sí** (`client.ts:310-312`). El agente tampoco puede cargar skills por el gap 1 (el `skill` tool sí está en V2, pero sin subagentes ni MCP el valor es limitado).
9. **[B/I] Renderizado de tools/reasoning/diffs muy por debajo de upstream**: sin reasoning, sin renderers para task/todo/read/webfetch, diff crudo en `<pre>`, highlighter regex, sin Shiki, sin comentarios en línea. Upstream lo tiene en `session-ui` y FlupCode no lo importa.
10. **[A] Sin cola/steer de prompts** aunque el cliente lo tiene plumbed (`client.ts:189`) y el TUI/app lo exponen.
11. **[E] Sin árbol/visor/búsqueda de archivos** (`fs.list/read`, `find.text/symbols` sin usar); la app oficial lo tiene.
12. **[A/C] Fork sólo de sesión entera; sin fork desde mensaje; sin marcadores de revert/compactación** en el timeline (el motor los emite).
13. **[C/G] Rutinas en el navegador** (`app.tsx:1508`): se duplican por pestaña/dispositivo, mueren al cerrar, sin historial. Necesitan un proceso del harness.
14. **[C] Artifacts que no son artefactos**: sin entidad, sin persistencia, sin producer ni contenido.
15. **[D] Ninguna primitiva de ejecución por encima de la sesión**: no hay Run/Task/Workflow; el supervisor de subagentes es una fila de chips (`SubagentList.tsx`).
16. **[F] Sin Context Inspector**: el usuario no puede ver qué instrucciones (AGENTS.md), skills, tools o MCP recibió el agente; el meter muestra tokens del último mensaje y nada más.
17. **[A] Permisos sin reglas visibles**: ni `always` guardados, ni editor de reglas, ni previews de diff/comando, ni pendientes cross-session en escritorio.
18. **[I] Accesibilidad y descubribilidad**: casi todos los diálogos sin Escape ni focus-trap (sólo `About` y la paleta gestionan Escape); split/rename/pin sólo en menú contextual (invisible en táctil); menú de perfil con 9 entradas duplicando la nav (`Sidebar.tsx:371-384`); `window.confirm`/`window.prompt` para acciones destructivas.
19. **[H] Lista de sesiones cap 200 sin paginación; home que descarga 30 transcripts para contar mensajes; caché de transcripts sin límite de tamaño** (`client.ts:174`, `client.ts:140`, `app.tsx:1103-1125`; se invalida por eventos `message.*` pero no hay LRU).
20. **[Docs/G] ROADMAP y PARITY no reflejan la realidad**: F3-7/8/10/13/17, F4-3/5/6, F2-2 marcados "done" están vacíos o rotos; el bloqueo de MCP es incorrecto; share "sin endpoint" es incorrecto. Esto es un riesgo de producto porque el roadmap futuro se planifica sobre una base que no existe.

## 4. Más allá de OpenCode: qué debería tener FlupCode

OpenCode es un **runtime**: sesión + loop de agente + tools + permisos + proveedores. Lo que hace de forma deliberadamente débil, y donde FlupCode puede ser categoría distinta, es todo lo que rodea al loop:

- **Ejecuciones durables por encima de la sesión (Run).** Una sesión de OpenCode es un chat con estado; un Run es un objetivo con plan, tareas, gates, artefactos, checkpoints, presupuesto y resultado, que sobrevive a cerrar el navegador y se puede supervisar desde el móvil. Ni OpenCode ni su app tienen esto; Claude Code lo tiene parcialmente (workflows, `/goal`) pero en terminal y opaco.
- **Supervisión visual de N agentes.** Ver qué hace cada agente, qué archivos toca, cuánto cuesta, dónde está bloqueado, y poder intervenir (steer, cancelar, reintentar, aprobar) sin abrir cada sesión. OpenCode lo reduce a pestañas de sesión hija.
- **Verificación como parte del harness, no del prompt.** Tests/lint/typecheck ejecutados por el harness con evidencia, reintentos acotados y veredictos estructurados (`format: json_schema` ya existe en el prompt legacy). OMC lo hace con prompts y hooks; OpenCode no lo hace.
- **Artefactos y checkpoints de primera clase.** Planes, specs, informes de test, reviews, diffs, capturas: navegables por proyecto, ligados al Run/tarea que los produjo, restaurables.
- **Context engineering visible.** Qué recibió el agente (instrucciones, skills, tools, MCP, system prompt), cuánto le queda, qué se compactó, y paquetes de contexto reutilizables entre tareas.
- **Políticas.** Permisos + selección de modelo + presupuesto por agente/rol/tarea, editables en UI, sin reescribir la configuración del proyecto.
- **Git como flujo, no como prompt.** Commit/branch/PR guiados, con revisión asistida por un agente que deja comentarios sobre el diff.
- **Operación remota y programada** (ya existe el sustrato): rutinas ejecutadas por un servicio, notificación y aprobación desde el teléfono.

Lo que **no** debería intentar: reimplementar el loop del agente, las tools, MCP o los proveedores; competir con Cursor en edición inline; construir un IDE; añadir más "chips" de features (comparaciones de tokens con libros, sugerencias por turno con sesiones ocultas) que consumen presupuesto y no mueven la aguja.

## 5. Qué significa "AI Coding Agent Harness"

| Nivel | Definición operativa | Ejemplos | Qué gestiona el sistema |
| --- | --- | --- | --- |
| **1. AI coding assistant** | Chat + sugerencias; el humano ejecuta cada paso | Copilot chat, Cline en modo chat | Nada: contexto y acción son del usuario |
| **2. AI coding agent** | Loop autónomo con tools, permisos y una sesión | OpenCode, Claude Code (una sesión), Aider, Codex CLI | El loop, las tools, los permisos, la compactación |
| **3. Agent harness** | Sistema alrededor de N agentes: ejecuciones durables, plan/tareas, delegación, contexto, políticas, verificación, checkpoints, observabilidad; el usuario sigue dirigiendo | Claude Code con teams/workflows/`/goal`, Cursor Agents Window, OMC sobre Claude Code | El ciclo de vida de la ejecución y la calidad del resultado |
| **4. Orchestration platform** | Muchos runs, programados, en la nube, multiusuario, colas, flota | Cursor Cloud Agents, Codex Cloud, OpenHands Cloud, Copilot coding agent | Infraestructura, entornos, gobernanza |

**FlupCode hoy está en el nivel 2 como UI** (y en el camino Code, por debajo de OpenCode por el runner V2). Tiene fragmentos del nivel 4 (remoto, push, rutinas) sin haber pasado por el 3. **La posición correcta es el nivel 3 con el sustrato remoto como diferenciador**: el "Agent Development Environment" del brief. El nivel 4 (nube, multiusuario) no es alcanzable ni deseable con el equipo actual, y el nivel 3 todavía no existe en el ecosistema open-source con GUI: la app oficial de OpenCode se queda en el 2, Cline Kanban es un preview, Claude Code lo hace sin GUI.

Capacidades que faltan para ser nivel 3, en orden de dependencia: (a) un proceso del harness fuera del navegador; (b) el modelo Run/Task sobre sesiones del motor; (c) supervisión y control (steer/cancel/retry/approve) por tarea; (d) verificación con evidencia; (e) artefactos y checkpoints; (f) políticas de permisos y modelo; (g) workflows declarativos; (h) paralelismo con aislamiento (worktrees); (i) observabilidad de tokens/coste/latencia por agente y tarea.

## 6. Plataforma de agentes: runtime, orquestación y supervisión

### 6.1 Lo que OMC enseña (y lo que no hay que copiar)

Oh My ClaudeCode 5.4 es útil como señal, no como plantilla. En su versión 5 retiró 17 nombres de modos (`ultrawork`, `ultrapilot`, `swarm`, `pipeline`, `ultraqa`…; `docs/MIGRATION.md` reconoce que `swarm`/`pipeline` "nunca se distribuyeron como skill") y se apoyó en lo que Claude Code fue haciendo nativo (agent teams, `/goal`, `model:` por subagente, worktrees). Su capa de **mecanismo** (persistencia vía Stop hooks que impiden al modelo parar, claiming de tareas a mano "porque no hay claiming atómico", inyección de `model` por hook, HUD leyendo `.omc/state`) es exactamente lo que un harness debe absorber como primitivas. Su capa de **proceso** es lo valioso y transferible:

| Problema que OMC resuelve | Mecanismo OMC | Primitiva nativa en FlupCode |
| --- | --- | --- |
| El agente declara "hecho" sin evidencia | `ralph`: PRD con criterios de aceptación, `passes:true` sólo con evidencia fresca (<5 min), revisión independiente, pase "deslop" | **Gate de verificación** en un Workflow: tarea de tipo `verify` con salida estructurada (`format: json_schema`) + comandos de test/lint del proyecto ejecutados por el harness |
| Planes de baja calidad | `ralplan`: planner → architect (steelman) → critic (independiente, sin ver al architect) → síntesis; máx 5 iteraciones | **Workflow "plan-consensus"** de 3 tareas con roles y visibilidad de contexto controlada (context pack sin el artefacto del otro revisor) |
| Perder el plan/decisiones al compactar | `.omc/notepad.md`, handoffs `.omc/handoffs/<stage>.md`, PreCompact checkpoint | **Checkpoint** (snapshot + resumen) al final de cada tarea y **Handoff note** como Artifact que se inyecta a la siguiente tarea |
| Coste de usar Opus para todo | tiers haiku/sonnet/opus por rol; Delegation Enforcer | **Policy de modelo por rol** (explore→barato, plan/review→razonador, execute→coding) |
| Sin visibilidad | HUD statusline | **Vista de supervisión** y **observabilidad** (§6.4, §13) |
| Ambigüedad antes de ejecutar | `deep-interview` con umbral de ambigüedad | Tarea `clarify` que usa el **question tool** (ya existe en el motor) al inicio de un Workflow |
| Aislamiento entre workers | worktree mode opcional | **Worktree por tarea** (`/experimental/worktree` ya existe) |
| Coordinación de equipo | native teams + mailboxes | **No** hacer mailboxes: dependencias en el grafo + artefactos como canal |

Lo que no hay que copiar: magic keywords en prosa detectadas por hook (frágil, opaco), 19 agentes con nombres cuya frontera hay que documentar, bucles "the boulder never stops" que fuerzan al modelo a no parar (en un harness el bucle lo controla el harness, con límites explícitos), y el shim sobre internals de la herramienta anfitriona. La lección de fondo: **OMC demuestra que los usuarios quieren proceso (plan → ejecutar → verificar → revisar) con evidencia; y demuestra que hacerlo con prompts y hooks es frágil.**

### 6.2 Modelo conceptual propuesto

Evaluación crítica de la hipótesis del brief (Agent + Task + Workflow + Skill + Context + Artifact + Checkpoint): es correcta en dirección, pero mezcla primitivas del **motor** (que ya existen y sólo hay que exponer) con primitivas del **harness** (que hay que crear). Separarlas evita reimplementar lo que OpenCode ya hace bien:

**Ya existen en el motor — exponer y editar, no rehacer:** Agent (`packages/core/src/agent.ts`: prompt, modelo, variante, tools, permisos, steps, modo primary/subagent, ficheros `.opencode/agents/*.md`), Session (con linaje `parentID`, snapshots, compactación, eventos durables), Skill, Tool (built-ins + MCP + plugin), Command, Model (catálogo, variantes, `small_model`), Permission (reglas por acción/patrón, `always` guardado).

**Nuevas, propiedad del harness:**

- **Run**: un objetivo del usuario en un proyecto; tiene un Workflow (o uno implícito de una sola tarea), un estado (`planning|running|waiting|verifying|done|failed|cancelled`), presupuesto, tareas, artefactos, checkpoints, resultado. Se materializa como una sesión raíz del motor (para el hilo con el usuario) y N sesiones hijas (una por tarea).
- **Task**: unidad ejecutable = `{agent, model?, variant?, input (prompt + context pack), permissions policy, workspace (dir o worktree), timeout, retries, gate?, dependsOn[]}`. Se ejecuta como una sesión del motor (hija del Run). Produce output (texto), diff, artefactos, tokens/coste, y opcionalmente un veredicto estructurado.
- **Workflow**: grafo declarativo de tareas con dependencias; v1 secuencial, v2 DAG con `parallel`. Guardado como fichero del proyecto (`.flupcode/workflows/*.yaml`) o global. Los "modos" de OMC son workflows.
- **Artifact**: `{id, kind (plan|spec|report|diff|log|file|screenshot|handoff|verdict), title, content|path, producer (run/task/agent), hash, createdAt, retention}`. Persistido por el harness; los planes del agente `plan` (`.opencode/plans/*.md`) se registran automáticamente.
- **Checkpoint**: `{run, task?, snapshot (git tree via `revert.stage`/`Snapshot`), summary (handoff), tokens, createdAt}`; restaurable. Automático al terminar cada tarea y manual desde la UI.
- **Policy**: conjunto nombrado de reglas de permisos + routing de modelo + presupuesto (`{permissions: rules[], models: {role→model/variant}, budget: {tokens?, usd?, minutes?}}`). Se aplica a un Run o a una Task **sin** modificar `opencode.json` del proyecto (hoy los modos PATCHean la sesión; eso es una Policy mal ubicada).
- **Context Pack**: conjunto reutilizable de referencias (`@archivo`, `@artifact`, `@handoff`, notas) que se inyecta como parts del prompt. Es la unidad de "compartir contexto entre agentes sin duplicar": las tareas reciben packs, no transcripts.

**Derivadas, no primitivas:** Agent Team = las tareas de un Run agrupadas por agente. Milestone = etiqueta sobre tareas. Todo = sigue siendo del agente (`todowrite`), visible pero no gestionado por el harness.

Con estas 6 primitivas nuevas se construyen feature development, bug fix, refactor, code review, security review, tests, docs, migración, research: cada uno es un Workflow + Policies + Context Packs, no una feature.

### 6.3 Runtime de orquestación: cómo se ejecuta

Dos modos de delegación deben coexistir:

- **Delegación dirigida por el agente** (ya existe en el motor): el agente primario llama al task tool o el usuario escribe `@explore …`. Ad-hoc, barata, no planificable. FlupCode debe mostrarla como tareas inline y en el supervisor.
- **Delegación dirigida por el harness** (nueva): `harness-server` ejecuta un Workflow: crea la sesión raíz, y por cada tarea lista (dependencias satisfechas) crea una sesión hija con el agente y policy indicados (`POST /session {parentID, permission}`), compone el prompt (objetivo + context pack + handoffs previos), envía por legacy `promptAsync` con `agent/model/variant` y, para gates, `format: json_schema`; se suscribe a los eventos de la sesión (`/event` o `sessions.events after` cuando sea V2) para estado, tools, tokens; espera idle; recoge el último texto, el diff (`/session/:id/diff`), los artefactos escritos; crea el checkpoint; evalúa el gate; decide reintento (misma sesión con feedback, hasta `retries`), fallo o continuación. Al final agrega resultados en la sesión raíz como mensaje + artefacto "Run report".

Reglas del runtime: paralelismo sólo entre tareas sin conflicto de escritura (misma `workspace` sólo si ambas son read-only; si no, worktree por tarea); límite de concurrencia global (por defecto 3); timeout por tarea con watchdog (sin eventos en N minutos → marcar `stalled`, notificar, ofrecer steer/cancel); cancelación propaga `abort` a todas las sesiones hijas; presupuesto: al superar el de la Policy, pausa el Run y pide confirmación (push al móvil); idempotencia: cada tarea registra `sessionID` y el `messageID` del prompt para reanudar sin duplicar tras un reinicio del harness.

Esto es esencialmente lo que Claude Code hace con `workflows` (`agent()/pipeline()/parallel()`) y OMC con hooks, pero declarativo, persistente y con GUI.

### 6.4 UX de supervisión

Vista "Run" (reemplaza al `SubagentList` de chips), con dos representaciones sincronizadas: **árbol** (por defecto) y **timeline** (gantt simplificado, útil con paralelismo). El grafo de dependencias sólo se dibuja en el editor de Workflows, no en ejecución: en ejecución un árbol con estados basta y es más legible.

```
Run: Implement authentication            ● running · 12m 40s · 184k tok · $1.92 · budget 65%
├─ 🧠 plan          planner · claude-fable · done 2m10s · 21k · $0.31   [plan.md ↗] [checkpoint]
├─ ⚙ backend       executor · gpt-6 · running 6m · 88k · $0.90 · 12 files · bash×14 edit×9
│    └─ ⏳ waiting permission: bash "bun test"           [Allow] [Always] [Reject] [Open]
├─ 🎨 frontend     executor · sonnet · running 5m · 61k · $0.44 · 4 files (worktree fe-1)
├─ 🧪 tests        verifier · queued (depends: backend, frontend)
└─ 🔍 review       reviewer · waiting
```

Por tarea, información mínima siempre visible: estado, agente, modelo/variante, duración, tokens y coste, archivos cambiados, tool actual (o último), bloqueo (permiso/pregunta) con acción inline. En detalle (panel lateral al seleccionar): reasoning summary (último bloque de reasoning), tools ejecutadas con duración y resultado, diff de la tarea, contexto consumido (% del límite del modelo) y qué contexto recibió (Context Inspector), errores y reintentos con motivo, dependencias, artefactos producidos, checkpoints, veredicto del gate, y acciones: abrir sesión, steer (mensaje a esa tarea), reintentar, cancelar, re-ejecutar desde checkpoint, cambiar modelo para el reintento.

A nivel de Run: presupuesto consumido, tareas por estado, tiempo estimado (por historial), y el "Run report" final. En el sidebar, bajo el proyecto, los Runs activos aparecen con un indicador de bloqueo (esto es lo que hoy falta: permisos de sesiones no seleccionadas invisibles en escritorio).

Los eventos que alimentan esto ya existen: `session.next.tool.called|progress|success|failed`, `session.next.step.*`, `permission.asked`, `question.asked`, `tokens` en cada mensaje asistente, `session.diff`. Falta sólo el reductor y la entidad Run/Task para agruparlos.

## 8. Session OS

Qué debería ser gestionar sesiones en un harness, y qué sustrato existe:

- **Jerarquía**: Proyecto → Runs (con sus tareas) y Sesiones sueltas (chat directo). Hoy los proyectos se derivan de `session.location.directory` (`app.tsx:989-1002`) y no existen sin sesión; el motor tiene `/project` — usarlo, y permitir "abrir carpeta" sin crear sesión.
- **Metadatos**: tags y favoritos via `PATCH /session {metadata}` (el motor no tiene tags pero sí `metadata: Record<string,string>`), archivado via `time.archived`, pins server-side (hoy localStorage, no viaja al móvil).
- **Búsqueda y filtro**: server-side (`GET /session?search=&roots=&limit=&start=` y `/experimental/session` con cursor y `archived`); filtros por proyecto, rama (`vcs.branch` en la sesión), agente, estado, coste. Eliminar el cap de 200.
- **Fork desde mensaje** y **linaje**: breadcrumb padre ▸ hijo; "abrir padre" desde una sesión hija; los forks como ramas visibles.
- **Checkpoints/snapshots**: cada mensaje de asistente ya lleva `snapshot.start`; exponer "restaurar archivos a este punto" con preview de diff (v2 `revert.stage` + `commit`) y marcador de revert en el timeline.
- **Replay**: reproducir una sesión V2 desde `sessions.events after` (útil para depurar runs y para compartir); para V1, replay de mensajes.
- **Export/share**: Markdown con opciones (con/sin tools, reasoning, diffs), JSON (`opencode export`), share con la infraestructura upstream (`/session/:id/share`); en el futuro, share propio en el harness-server.
- **Comparación**: dos sesiones/tareas lado a lado por tokens, coste, duración, archivos, veredicto — es la base para "best-of-n" (Cursor) sin construir best-of-n.
- **Stash de prompts**: mover de localStorage al harness-server para que viaje entre dispositivos.
- **Analítica**: `opencode stats`-like en servidor; el dashboard actual descarga transcripts (`app.tsx:1103-1125`) y debe desaparecer en su forma actual.

## 9. Context engineering

Qué contexto compone hoy el motor por sesión (verificado en `CONTEXT.md` y `core/src/system-context/*`): entorno, fecha, built-ins, guía de skills disponibles para el agente, instrucciones (`AGENTS.md` global + ascendentes; legacy también `CLAUDE.md` y `instructions[]`), y el historial proyectado desde la última compactación. Ni la UI de OpenCode ni FlupCode enseñan nada de esto; `sessions.context` devuelve sólo mensajes.

Evaluación de las ideas del brief, con criterio de utilidad real:

- **Context Inspector — muy útil, hacer en Fase 1.** Panel por sesión/tarea con: ficheros de instrucciones encontrados y su orden (el motor lo sabe; hay que exponerlo via plugin o leerlos desde el harness-server con la misma lógica de descubrimiento), skills listadas al agente (`GET /skill` filtrado por permisos del agente), tools disponibles (`/experimental/tool/ids` para el modelo), servidores MCP conectados y sus tools, system prompt final (capturable con el hook de plugin `experimental.chat.system.transform`, que FlupCode ya podría registrar desde su plugin de motor), tokens del último turno por categoría y % del límite. Responde a la pregunta "¿por qué el agente hizo esto?" que hoy no tiene respuesta.
- **Context Budget — útil, ampliar lo que existe.** El `ContextMeter` ya muestra tokens/coste; falta por tarea, por Run, contra presupuesto de Policy, y con aviso de compactación inminente (`compaction.buffer`).
- **Compactación visible — útil, barata.** Marcador en el timeline con el resumen generado (es un mensaje) y "qué se podó" si `compaction.prune`; botón manual (`/compact`) ya existe.
- **Context Pack — útil, es la primitiva de compartir contexto.** Packs guardados por proyecto (archivos, símbolos vía `/find/symbol`, artefactos, notas); se inyectan como parts (`file` parts legacy admiten `mention`). Evita copiar contexto entre sesiones a mano.
- **Handoff notes — útil, pequeño.** Al cerrar una tarea, el harness pide (con `small_model`) un resumen "decidido / rechazado / riesgos / archivos / pendiente" de 10–20 líneas como Artifact y lo mete en el pack de la siguiente tarea. Es la idea buena de OMC.
- **Context Checkpoints — no como entidad aparte.** Un Checkpoint ya guarda snapshot + resumen; el "contexto" de una sesión V2 es reproducible por eventos durables. Sobreingeniería crearlos separados.
- **Context Diff entre ejecuciones — sobreingeniería ahora.** Sólo tiene sentido cuando existan Runs repetibles (rutinas/workflows); dejar para P3 como "diff de packs + instrucciones".
- **Smart Context automático (embeddings, selección por relevancia) — no ahora.** El agente `explore`, `grep`, `/find/symbol` y las referencias (`references` config) cubren el 80%; un índice semántico es una inversión grande con beneficio incierto y la app perdería explicabilidad. Reevaluar en P3.
- **Memoria de proyecto** (más allá de AGENTS.md): notas del harness por proyecto (decisiones, convenciones aprendidas) que se inyectan como instrucción adicional (`instructions[]` acepta rutas) — pequeño y útil; no construir un sistema de memoria general.

## 10. Skills, MCP y comandos

### 10.1 Skills

Cómo debería sentirse frente al TUI: en el TUI las skills son invisibles hasta que el agente decide cargarlas. En FlupCode deberían ser un **catálogo por proyecto** con origen (`.opencode/skills`, `.claude/skills`, `.agents/skills`, global, `skills.urls`), descripción, tamaño, ficheros adjuntos, qué agentes las ven (derivado de reglas `skill` por agente), diagnósticos (nombre ≠ carpeta, frontmatter inválido, duplicados que se sombrean, descripción > 1024) y uso (cuántas veces la cargó un agente: evento de tool `skill`). Acciones: previsualizar `SKILL.md`, activar/desactivar por agente (escribe reglas `skill` en el agente), instalar desde URL o ruta (`skills.urls/paths` via `PATCH /config`), crear/editar (requiere escritura de ficheros: harness-server o `!` — no hay endpoint de escritura), invocar: "pedir al agente que use la skill X" = prompt con instrucción explícita (no existe endpoint `session.skill`; el stub actual debe ir). Un **Skill Manager** real es viable en Fase 1 con lo anterior; el "marketplace" es P3 (bastaría un índice de URLs `.well-known/skills`).

### 10.2 MCP

Sustrato existente en legacy: `GET /mcp` (estado por servidor), `POST /mcp` (añadir), `/mcp/:name/connect|disconnect`, OAuth (`/auth`, `/auth/authenticate`, `/auth/callback`, DCR automático), `/experimental/resource`, evento `mcp.tools.changed`, config `mcp.<name>` local/remoto con `timeout`, `environment`, `headers`, `enabled`. Lo que no está: logs por servidor, latencia, prompts MCP, health histórico. Propuesta de UX: lista de servidores con estado (connected / failed / needs auth / disabled), tools expuestas (`<server>_<tool>`) con descripción, recursos, "probar tool", latencia media y errores (el harness-server las mide desde `tool.called→success|failed` para tools `server_*`), botones connect/disconnect/auth, editor de configuración con formulario (no JSON), acceso por agente (reglas `server_*` en tools/permisos del agente) y por proyecto (`opencode.json` del proyecto vs global). Catálogo: P3. Primera acción concreta: sustituir los stubs de `client.ts:451-457` por las llamadas del SDK (`client.mcp.*`) — es trabajo de un día, y la razón de "bloqueado" en el ROADMAP es falsa.

### 10.3 Comandos

El motor los ejecuta con `agent/model/variant/subtask`, `$ARGUMENTS`, `$1..$N`, `` !`shell` `` y `@archivo`. FlupCode los lista y ejecuta sin overrides. Propuesta: editor de comandos (formulario sobre `.opencode/commands/*.md` o `command` en config), argumentos con placeholders en el composer, badge de origen (proyecto/global/plugin/MCP prompt), y —lo importante— **un comando es un Workflow de una tarea**: el launcher de workflows y el de comandos deberían ser la misma superficie (`/` en el composer y la paleta) con tres tipos: comando (prompt con plantilla), skill (instrucción de cargar) y workflow (Run). Así se responde a "¿prompts, commands, skills, agents, workflows o routines?": **commands para plantillas de prompt de una sesión; skills para conocimiento reutilizable que el agente carga; agents para roles; workflows para procesos con varias tareas y gates; routines para workflows programados.** Los cinco existen como conceptos distintos porque tienen dueños y ciclos de vida distintos; lo que debe unificarse es el lanzador.

## 11. Ciclo de trabajo de código y Git/Code review

### 11.1 Dónde eliminar fricción en el ciclo

| Paso | Hoy en FlupCode | Qué debería hacer el harness |
| --- | --- | --- |
| Prompt | texto libre | Launcher unificado: prompt, comando, skill o workflow; clarificación opcional con question tool |
| Planning | agente `plan` si el usuario lo elige | Workflow con tarea `plan` que produce Artifact `plan.md`, aprobación explícita (gate humano) antes de ejecutar |
| Context gathering | manual (`@ruta`) | Context packs, handoffs, Context Inspector |
| Ejecución | una sesión | Tareas con policy, worktree si hay paralelismo |
| Tool calls | visibles a medias | Renderers completos + timeline de tools con duración |
| Cambios | patch crudo | Diff estructurado por tarea/turno con comentarios |
| Tests | el agente decide | Tarea `verify` del harness: ejecuta `test/lint/typecheck/build` del proyecto (detectados o configurados en `.flupcode/project.yaml`), parsea salida, evidencia como Artifact, reintento acotado con feedback al ejecutor |
| Review | prompt manual | Tarea `review` con agente revisor, salida estructurada (findings con archivo/línea/severidad), comentarios en el diff |
| Fixes | otro prompt | reintento automático de la tarea ejecutora con los findings como input, hasta N |
| Verificación | ninguna | veredicto del gate + evidencia |
| Commit | prompt "Commit the current changes…" | Commit UI: mensaje generado con `small_model`, staging por archivo/hunk, firma del harness |
| PR | manual | `gh pr create` desde harness-server con cuerpo = Run report + artefactos |

### 11.2 Git

Existe en el motor: `/vcs` (rama), `/vcs/status`, `/vcs/diff` estructurado, `/vcs/diff/raw`, `/vcs/apply`, `/file/status`, snapshots por mensaje, `session.diff`, `/project/git/init`, worktrees. No existe: commit, branch, stash, PR. Dos caminos: usar `!git …` via `session.shell` (rápido pero opaco) o dar al harness-server operaciones git propias (recomendado: `simple-git`/`git` CLI en el proceso del harness, que además necesita worktrees y PR). Propuesta de superficie: barra de repo con rama y estado; panel de cambios con árbol de archivos, diff Pierre (via `session-ui/pierre`) por archivo y hunk, stage/unstage por hunk (`git apply --cached` de hunks), revert selectivo por archivo (ya posible con `revert.stage {files}`), "explicar este cambio" (prompt con el hunk), commit con mensaje generado y editable, crear rama, crear PR con plantilla. Resolución de conflictos: no en los 6 meses; al mergear worktrees, si hay conflicto, crear una tarea `resolve-conflicts` con un ejecutor y mostrar el resultado; el humano decide.

### 11.3 Code review como composición de primitivas

`Review = Workflow{ tasks: [analyze-diff(explore) → security(reviewer, pack: diff+OWASP-skill) ∥ quality(reviewer, pack: diff+AGENTS.md) → summary(writer) ] }` con findings estructurados que el visor de diff pinta como comentarios de línea (upstream ya tiene `context/comments.tsx` y `line-comment-styles` en session-ui). Con esto salen gratis security review, test review, architecture review y "risk analysis" (un reviewer con pack distinto). Además el motor trae un comando `review` built-in (`opencode/src/command/template/review.txt`) que sirve como primera versión de una sola tarea.

## 12. Artifacts, Workflows y Routines

### 12.1 Artifacts

Sí, FlupCode debe tener un sistema de artefactos, pero como **índice + almacén ligero**, no como CMS: `{id, projectID, runID?, taskID?, sessionID?, kind, title, mime, content (texto ≤1 MB) | path (fichero del repo o del almacén del harness), hash, producer (agent|user|harness), createdAt, expiresAt?}`. Fuentes automáticas: planes (`.opencode/plans/*.md` escritos por el agente `plan`), ficheros creados por `write` marcados por el usuario como artefacto, informes de verificación y review (harness), handoffs, Run reports, exports de sesión, diffs por tarea, capturas de pantalla (adjuntos), logs de tools truncados (`Managed Tool Output File` ya existe en el motor: exponer su ruta). UX: panel por proyecto con filtros por kind/run/fecha, visor (markdown, diff, imagen, log), "abrir en el editor", "añadir al contexto" (crea un `@artifact` en el pack), "fijar" (aparece en el sidebar del proyecto). El panel actual (`ArtifactsPanel.tsx`) se reemplaza; la idea de listar archivos tocados sobrevive como filtro "archivos de esta sesión".

### 12.2 Workflows

Formato declarativo mínimo (v1):

```yaml
name: feature
description: Plan, implement, verify and review a feature
inputs: [goal]
tasks:
  - id: plan
    agent: plan
    prompt: "Create an implementation plan for: {{goal}}"
    artifacts: [plan]              # registra .opencode/plans/*.md
    gate: human                    # el usuario aprueba el plan
  - id: implement
    agent: build
    dependsOn: [plan]
    context: [artifact:plan]
    policy: coding
  - id: verify
    kind: verify                   # tarea del harness, no LLM
    dependsOn: [implement]
    commands: [test, typecheck, lint]
    onFail: { retry: implement, max: 2 }
  - id: review
    agent: reviewer
    dependsOn: [verify]
    context: [diff:implement, artifact:plan]
    output: findings               # json_schema → comentarios en el diff
```

v2 añade `parallel: true` por tarea, `workspace: worktree`, `foreach` (una tarea por elemento del plan) y `when` (condiciones sobre veredictos). Las plantillas iniciales son las del brief: feature, bugfix (investigate → reproduce → fix → verify → review), refactor, review; se distribuyen como ficheros editables, no como código. Un Workflow se lanza desde el composer (`/feature …`), la paleta o un botón en el proyecto; se puede "ejecutar hasta la tarea X" y "reanudar desde checkpoint".

### 12.3 Routines

Una Routine es `{workflow|prompt, project, schedule (cron), policy, notify}` ejecutada por el harness-server (cron en proceso, con lock por rutina para evitar duplicados y con historial de runs). Cada ejecución es un Run normal (supervisable, con artefactos). Casos: "cada mañana revisa PRs abiertos", "cada noche corre la suite y abre issues", "semanalmente auditoría de dependencias". Sustituye el `setInterval` actual. Notificación por push al móvil (ya existe el canal) con enlace al Run.

## 13. Observabilidad, routing de modelos, fiabilidad y seguridad

### 13.1 Observabilidad

El usuario debería ver, por Run/tarea/sesión: timeline de tools (`tool.called → success|failed`, duración, bytes de salida, truncados), llamadas al modelo (por `step`, con tokens input/output/reasoning/cache, coste, latencia, reintentos `session.status retry`), MCP (latencia y fallos por servidor), shell/PTY, permisos pedidos y decididos, compactaciones, errores del proveedor (`session.error`). Todo sale de eventos que ya existen; el harness-server los persiste en su SQLite (tabla `events` desnormalizada por run/task/tool) y la UI ofrece: (1) barra de estado por sesión (lo que hace el `ContextMeter`, ampliado), (2) panel "Actividad" por Run con timeline y filtros, (3) dashboard por proyecto (tokens/coste por modelo, agente, workflow; tools más lentas; tasa de reintentos; sesiones bloqueadas). Exportable a JSON/OTel (el motor tiene `experimental.openTelemetry`). Esto reemplaza el dashboard actual computado en cliente.

### 13.2 Routing de modelos

Sí a **perfiles** (Policy): `{explore: cheap, plan: reasoning-high, implement: coding, verify: n/a, review: reasoning, summarize: small_model}`, editables, con presupuesto. Sí a **fallbacks** por proveedor caído (el motor sólo reintenta; el harness puede reintentar la tarea con el modelo alternativo del perfil tras N fallos 5xx/overloaded, que se ven en `session.status retry` y `session.error`). Sí a **presupuestos** por Run (tokens/USD/tiempo) con pausa y confirmación. No a routing automático por "dificultad estimada" con un clasificador: opaco, difícil de depurar y el usuario perdería control; en su lugar, el perfil por rol de tarea cubre el caso y es explicable. "Model health" = simplemente latencia y tasa de error observadas por modelo en el dashboard.

### 13.3 Fiabilidad y recuperación

Escenarios y respuesta propuesta:

- **Cuelgue del agente/tool**: watchdog por tarea (sin eventos en N min → `stalled`), timeout de bash ya existe (2–10 min); acción: notificar, ofrecer `interrupt` + reintento.
- **Fallo de red / SSE medio abierto**: idle timeout de 25 s usando `server.heartbeat`, reconexión con backoff, `Last-Event-ID`/`after` para V2, refetch de permisos/preguntas/estado al reconectar, pill "reconectando" (hoy: cuelgue silencioso, `client.ts:24-58`).
- **Timeout del modelo / 429 / 5xx**: reintentos del motor legacy (hasta 5 con `retry-after`) visibles en UI; a nivel de tarea, fallback de modelo por Policy.
- **Tool call malformada / doom-loop**: `invalid` tool y `doom_loop` permission del legacy; UI que lo muestre como tal (hoy invisible).
- **Fallo MCP**: estado por servidor, reconexión manual/auto, la tarea sigue si la tool no es crítica.
- **Ejecución parcial**: el checkpoint de fin de tarea + `sessionID` persistido permiten reanudar el Run desde la última tarea completa sin repetir trabajo.
- **Desconexión del navegador / cierre de pestaña**: nada se pierde si el Run vive en el harness-server; al volver, la UI reconstruye desde estado + eventos.
- **Reinicio del backend**: el motor V2 deja prompts admitidos pendientes sin continuación automática (`llm.ts:86`); el legacy marca tools huérfanas como interrumpidas. El harness-server, al arrancar, revisa Runs `running`, comprueba el estado de sus sesiones y reanuda o marca `interrupted` con acción "reanudar".
- **Cancelación**: propagación a todas las sesiones hijas + limpieza de worktrees opcional.
- **Idempotencia**: `messageID` explícito en prompts (el SDK lo admite) para no duplicar al reintentar la llamada HTTP.

### 13.4 Seguridad

Modelo propuesto para un harness con control remoto:

- **Permisos**: la fuente de verdad es la configuración del proyecto/agente; los "modos" de la UI se convierten en Policies que sólo pueden **restringir** (añadir `ask`/`deny`), nunca ampliar silenciosamente; un modo `bypass` existe pero es explícito, no persistente, visible (pill rojo) y no aplicable desde un dispositivo remoto sin reconfirmar en el escritorio. Previews de diff/comando en cada prompt de permiso; `always` guardados listados y revocables; `external_directory` siempre `ask`.
- **Shell (`!`)**: chip distinto en el composer, confirmación en remoto, registrado como acción del usuario en el transcript.
- **Secretos**: el motor debería devolver `hasKey` en lugar de la clave (cambio upstream a proponer; mientras tanto, no pedir `/provider` sobre el túnel y eliminar el auto-import de claves); credenciales del proveedor sólo por `PUT /auth`.
- **Electron**: `webSecurity:true`, `sandbox:true`, esquema `app://` para el renderer, `setWindowOpenHandler` → `shell.openExternal`, `will-navigate` denegado, iframe del navegador con `sandbox` y `referrerpolicy`, motor local con contraseña generada (`OPENCODE_SERVER_PASSWORD`) pasada por el bridge y el túnel.
- **Remoto**: PSK como `CryptoKey` no extraíble en IndexedDB en vez de `localStorage`; allowlist de rutas en el host del túnel (nada de `/auth`, `/config`, `/provider` desde el móvil por defecto); límite por IP por host en el relay; el diálogo de emparejamiento explica el alcance.
- **Aislamiento de agentes**: worktree por tarea para escritura paralela; tareas de research con Policy read-only; `subagent_depth` configurable; repos no confiables: Policy "untrusted" (deny bash salvo allowlist, deny webfetch a no-allowlist).
- **Prompt/tool injection**: los outputs de tools y MCP se renderizan como datos (DOMPurify con `FORBID_TAGS: img/svg/iframe`, `ALLOWED_URI_REGEXP` https), los findings del reviewer nunca se ejecutan automáticamente, skills/MCP nuevos requieren confirmación del usuario la primera vez que un agente los usa (permiso `skill`/tool `ask` por defecto para fuentes remotas).

## 14. Rendimiento

Problemas verificados y solución concreta (severidad):

- **Refetch completo por evento** (`app.tsx:667-690`, `client.ts:322-340`) — alta. → Store por id, reductor de eventos, `reconcile` con `key:"id"`, `<For>` por id, paginación de mensajes (`GET /session/:id/message?limit&before` existe).
- **Live text O(n²) y re-parse de markdown por token** (`app.tsx:726`, `SessionView.tsx:754-758`, `Markdown.tsx:30`) — alta. → Batching por `requestAnimationFrame`, aplicar deltas al part del store (una sola fuente de verdad, sin efecto de "catch-up"), markdown incremental (`session-ui/markdown-stream` + `markdown-cache` ya lo resuelven) o al menos parsear sólo el último bloque.
- **Diff LCS O(n·m) y regex compiladas por celda en hilo principal** (`highlight.ts:87-96`, `:185-193`, llamada por celda en `SessionView.tsx:118`) — media. → `session-ui/pierre` (o Myers + worker), caché de regex por lenguaje, cap de líneas resaltadas.
- **`querySelectorAll`+`getBoundingClientRect` por scroll y regex de commit por render** (`SessionView.tsx:564-587`, `316-334`) — media. → `IntersectionObserver`, memo por mensaje.
- **Home N+1** (`app.tsx:1103-1125`) y **caché de transcripts sin límite de tamaño** (`legacyHistory`, `client.ts:140`; se invalida por sesión pero sin LRU) — media. → contadores desde la lista de sesiones / harness-server, LRU.
- **Lista de sesiones cap 200** (`client.ts:174`) — media. → cursor.
- **Paneles múltiples multiplican requests** (`SessionPane.tsx:98-108`) — media. → un único store compartido y suscripción por sesión.
- **PUT `/pty/:id` por tick de `ResizeObserver`** (`Terminal.tsx:53-57`) — baja. → throttle.
- **Bundle**: sin `manualChunks`, tailwind incluido sin usarse, deps declaradas sin usar — baja. → limpieza.
- **Persistencia**: mover pins/stash/rutinas/historial al harness-server; IndexedDB para caché de transcripts (opcional, después del store).
- **Escenarios de escala**: con miles de mensajes y cientos de tool calls, los cuatro primeros puntos hacen inusable la app; con varios agentes, el `runState` se reconstruye por evento (`app.tsx:120-125`) y cada pane refetchea. Objetivo medible tras la Fase 0: un turno con 200 tool calls no debe generar más de 1 request por evento de step y ningún re-montaje del timeline.

## 16. Análisis competitivo

Estado verificado en septiembre de 2026 (fuentes: docs oficiales; OMC desde su repo).

**Paridad de features.** OpenCode (runtime) es la base: agentes/subagentes con `background` experimental, skills, comandos, MCP con OAuth, plugins, LSP, permisos por patrón, fork, revert por snapshot, compactación, worktrees experimentales, SDK/servidor. Claude Code 2.1.x añade sobre ese nivel: subagentes con `isolation: worktree`, `memory`, `hooks` por agente; agent teams con lista de tareas compartida y claiming con lock; workflows scriptados (`agent/pipeline/parallel`, hasta 16 concurrentes); `/goal` (evaluador en Stop); `/loop` y rutinas; ~30 eventos de hooks; `/rewind` (código y/o conversación); `/usage` con atribución a skills/subagentes/MCP; `/code-review ultra`. Cursor: subagentes, plan mode con planes como ficheros, `/worktree`, `/best-of-n`, Cloud Agents, BugBot. Codex: subagentes (`max_threads` 6, `max_depth` 1), Automations programadas, `/review`, cloud. Copilot: coding agent en Actions, custom agents en `.github/agents`. Cline: Plan/Act, checkpoints, subagentes read-only, Kanban con worktrees (preview) que orquesta incluso OpenCode. Roo Code: cerrado en mayo de 2026. Aider: architect/editor, repo map, auto-commit, lint/test loops; sin multiagente. OpenHands: SDK, sandboxes, Task tool síncrono, critic experimental, evaluación. OMC: proceso (PRD, consenso, verificación con evidencia, handoffs, HUD) sobre Claude Code.

**Dónde puede FlupCode ser superior y dónde no:**

1. *Feature parity*: por debajo de todos hoy en el camino Code (gap 1). Tras la Fase 0, a la par con la app oficial de OpenCode.
2. *UX*: la app oficial de OpenCode es la referencia inmediata (tabs, árbol, review); ninguna herramienta tiene supervisión visual de runs multiagente con GUI + móvil: es el hueco. Claude Code lo hace en terminal; Cursor lo hace por worktree en la Agents Window sin grafo ni gates; Cline Kanban es lo más cercano y es un preview.
3. *Arquitectura*: OpenCode tiene el mejor sustrato abierto (servidor + SDK + eventos durables); Claude Code es cerrado; FlupCode hereda el sustrato y puede añadir un servicio de harness encima. Ventaja real si no se rompe la regla de upstream read-only.
4. *Orquestación*: Claude Code (teams + workflows + `/goal`) es el líder; FlupCode puede igualar el modelo (DAG declarativo + gates) y superarlo en visibilidad y control (steer/retry/cancel por tarea desde GUI y móvil).
5. *Workflows*: Codex Automations y Claude routines cubren programación; nadie ofrece workflows declarativos editables con gates de verificación en GUI. Oportunidad clara.
6. *Contexto*: Claude Code (`/context`, auto memory, rules por ruta) y Aider (repo map) van por delante; FlupCode puede ganar en **transparencia** (Context Inspector, packs, handoffs), no en automatismo.
7. *Productividad*: Cursor/Copilot ganan en edición inline; FlupCode no debe competir ahí. Gana si el ciclo plan → ejecutar → verificar → revisar → PR se hace con menos prompts y con evidencia.

**Corrección a H-01, confirmada al ejecutarlo.** La ficha lo estima en M ("prompt por
`promptAsync`"). Medido contra el motor local el 16/09/2026, el coste real es mayor y la razón es el
stream de eventos:

- `/api/event` (el que consume el harness) sólo lleva los eventos del runner V2: en la prueba
  aparecen `session.next.*` de otra sesión activa y **ningún** `message.*`.
- Un turno del runtime legacy —lanzado con `POST /session/:id/shell`, que no gasta modelo— se
  ejecuta correctamente y no emite nada en `/api/event`. Sus `message.*` y sus deltas sólo salen por
  `/event?directory=…`, que filtra por directorio (por eso la pestaña Chat ya se suscribe ahí,
  `app.tsx`, "Chats run through the legacy prompt…").

Mover Code al runtime legacy no es cambiar la llamada de prompt: obliga a que la app se suscriba a
un stream por cada directorio que muestra y a reconciliar desde ahí, que es justo lo que hace la app
oficial. Es decir, **H-01 arrastra a H-02**: conviene hacerlos como un solo bloque (intake de
eventos por directorio + store por eventos) y no en ese orden. Reestimación: L, riesgo 3.

Otras tres cosas medidas contra el motor local, que la auditoría no recogía y que cambian el diseño:

- **Un solo almacén de sesiones.** `/session` y `/api/session` listan las mismas sesiones, y el
  runtime legacy corre sin problema sobre una sesión creada por V2. No hace falta migrar nada.
- **Dos tablas de mensajes, confirmado.** Un turno legacy escribe solo en `/session/:id/message`;
  `/api/session/:id/message` se queda vacío. La fusión de ambas listas sigue siendo necesaria para
  las sesiones antiguas.
- **`/api/session/active` solo ve runs V2.** Durante un turno legacy no aparece ahí. El equivalente
  es `GET /session/status?directory=`, por carpeta. Sin esto, cada reconexión marcaba como inactiva
  una sesión que estaba trabajando.
- **El legacy no tiene cola.** Un prompt enviado a una sesión ocupada lo absorbe el bucle en curso
  (`Runner.ensureRunning`), es decir, siempre *steer*. Encolar pasa a ser trabajo del harness, lo
  que de paso hace cancelable un prompt en cola — la parte que H-07 tuvo que dejar fuera.
- **El motor solo titula si el título sigue su patrón por defecto** (`isDefaultTitle`). Renombrar la
  sesión con la primera línea del prompt, como hacía el harness, impedía para siempre que el motor
  la titulara.

**Lo que H-22 dejó medido** (16/09/2026). Una tarea `verify` es una tarea del run como cualquier otra
salvo en una cosa: no toca el motor. Corre los comandos del proyecto y guarda lo que imprimieron, así
que cuesta tiempo y no tokens — que es lo que la hace ejecutable después de cada intento y no una vez
al final. El test que la cubre usa un motor que lanza excepción si alguien lo llama, para que eso no
se pierda por accidente.

De dónde salen los comandos: `.flupcode/project.yaml` bajo `verify` si existe, y si no, los scripts
`typecheck`, `lint`, `test` y `build` que ya tenga el `package.json`, con el gestor que diga su
lockfile. Declarar gana entero: a un repositorio que dice cómo se comprueba no se le añaden pasos
que no pidió. Y **no se inventa nada**: un proyecto sin ninguno de esos scripts da veredicto
*failed* con "No verification", no un verde.

Medido contra el servidor real, con un proyecto que falla a propósito:

```
POST /harness/runs  {"tasks":[{"name":"verify","kind":"verify"}], "directory": …}
run.status  = failed
task.error  = Verification failed: test
task.output = - typecheck (echo "no type errors") — ok, 0.0s
              - test (…; exit 1) — exit 1, 0.0s
              ### test
              expected 1, got 2
```

**El reintento acotado**, con la decisión que quedaba pendiente resuelta: un reintento es una
**tarea nueva**, no la misma repetida. Repetir la fila borraría lo que hizo, dijo y costó el primer
intento, y todo este ticket va de conservar evidencia — quien lo lea tiene que poder ver que el
primero falló, qué se le dijo al segundo y qué cambió. También mantiene honestos los totales: dos
intentos cuestan dos intentos. Eso fija el terreno para H-15 (un checkpoint cuelga de un intento) y
H-28 (el DAG ordena tareas, y un reintento es una de ellas).

El presupuesto viaja con la tarea `verify` y se gasta al usarse: la que programa un reintento nace
con uno menos, así que un run no puede dar vueltas pase lo que pase. El tope es 5 —cada reintento es
un turno de modelo más otra ronda de comandos— y la API lo recorta, porque un número escrito por
error no debe poder gastarse una tarde.

Al ejecutor se le devuelve su propio prompt más lo que dijo la comprobación. Nada más: el harness
sabe qué falló, no cómo arreglarlo, e inventar consejo aquí sería poner palabras delante de la
evidencia.

Lo que el ticket pide y **sigue sin estar**: la evidencia como Artifact. Vive en el `output` de la
tarea porque el almacén de H-14 no existe.

**Lo que H-21 dejó medido** (16/09/2026). Un workflow es un fichero y lo que produce es un run de
tareas — nada más. El supervisor, el stream, la verificación y el reintento funcionan sobre él sin
enterarse de que había un workflow detrás, que era la prueba de que el modelo de H-11 estaba bien
puesto.

Las cuatro plantillas (feature, bugfix, refactor, review) se escriben en
`~/.local/share/flupcode/workflows` **una vez y nunca se sobrescriben**: una `feature` editada es
justo el motivo de distribuirlas como ficheros. Las de un proyecto (`.flupcode/workflows/*.yaml`)
ganan a las compartidas.

El **gate humano** para el run donde está la tarea y lo deja en `awaiting`, un estado que no es
ejecutando ni terminado. Solo hay dos respuestas: dejarlo pasar (`POST /harness/runs/:id/approve`) o
pararlo, que es rechazarlo. Un run en la puerta no se puede borrar ni se lo lleva «limpiar
terminadas», porque no es historia.

Medido contra el servidor real:

```
1) tras la tarea con puerta:  run: awaiting  tareas: think=success, check=queued
2) tras dejarlo pasar:        run: success   tareas: think=success, check=success
   rechazarlo en la puerta:   run: stopped   tareas: think=success, check=queued
   borrarlo en la puerta:     409 Stop the run before deleting it
   limpiar terminadas:        removed 3, y el que esperaba sigue ahí
```

Esa prueba encontró un fallo que los tests no: la comprobación de la puerta estaba después de la
rama de agente, y la rama `verify` salía por `continue`, así que una tarea `verify` con `gate: human`
pasaba de largo. Los tests unitarios usaban una tarea de agente y no lo veían.

Para guardar dónde trabaja un run hizo falta una columna nueva en `runs`: un run recogido diez
minutos después no tiene a nadie sujetando los argumentos con los que se lanzó.

El **launcher** es el mismo que ya había: un workflow es un comando más. Sale en la lista de `/` del
composer y en la paleta, junto a los comandos del motor y las skills, porque «launcher unificado»
quiere decir exactamente eso y no un menú aparte. Lo que se escriba detrás del nombre llena su primer
input — `/feature añade búsqueda a la barra lateral` — y al lanzarlo te deja en Ejecuciones, porque un
run que nadie ve es justo lo que esto viene a sustituir. Un workflow que pide más de un input no cabe
en una línea y lo dice, en vez de arrancar con el resto vacíos.

Lo que el ticket pide y **no está**: la **salida estructurada** del gate de review (`output:
findings` → comentarios en el diff), que es H-32. Tampoco `dependsOn` (el orden es la dependencia; el
DAG es H-28) ni `context:`/`artifacts:` (H-14).

**H-20 — commit sin pagar un turno** (16/09/2026). `commitChanges` escribía
`"Commit the current changes with a clear message."` en el composer y lo enviaba. Cada commit era un
turno de modelo, cobrado, para ejecutar dos órdenes — y sin ver qué se iba a confirmar.

El servidor es la única parte de FlupCode que puede ejecutar git: el cliente es un navegador y las
rutas `/vcs` del motor sólo leen. `POST /harness/git/commit` y `/harness/git/branch` lo hacen con un
vector de argumentos, nunca por un shell, y **sólo aceptan rutas que `git status` acaba de listar
como cambiadas** — la confinación que H-47 pide, aplicada donde se escribe. Verificado contra un
repositorio real: una ruta `../../etc/hosts` se rechaza, y un mensaje con `"; touch …; echo "` acaba
siendo el asunto del commit y nada más.

Del ticket falta el stage por hunk, el revert selectivo, el mensaje generado y el PR. **No** hay
descartar ni resetear a propósito: un commit y una rama se deshacen con git, un cambio sin confirmar
que se tira no.

**H-20 — el PR y su CI, en la cabecera** (16/09/2026). Lo que quedaba del ticket salvo el stage por
hunk, el revert y el mensaje generado. Un `gh pr list` trae el número, el estado, el tamaño y todos
los checks con su veredicto, así que el chip es una llamada, sondeada cada 20 s mientras el CI corre
y cada dos minutos cuando ya no.

Un detalle que habría sido un fallo silencioso: **`gh` elige el repositorio por defecto de la
carpeta**, y en este fork eso es `anomalyco/opencode`, no `rldona/FlupCode`. Un `gh pr list` a secas
devuelve `[]` para una rama que sí tiene PR — sin error, sólo el repositorio equivocado. El servidor
lo saca del remoto de la propia rama (`@{push}`, luego `@{upstream}`, luego `origin`) y lee la URL
con `git config --get`, no con `git remote get-url`, que aplica los `insteadOf` y devolvería una ruta
local sin dueño ni nombre.

Dos cosas más que encontraron las pruebas, no el razonamiento. **`Bun.spawn` lanza** cuando el
binario no está en el PATH en vez de devolver un código de salida: sin `gh` instalado, el endpoint
cuya única función es decir que falta habría respondido un 500. Y el veredicto verde ahora exige que
**algo haya pasado de verdad**: checks todos saltados dejan el punto gris, porque no avalan nada.

Sin `gh`, o sin sesión iniciada, no se dibuja chip — no un chip que no puede decirte el estado.

**Por qué falló el CI** (16/09/2026). El chip decía «2 han fallado» y ahí se acababa: la respuesta
estaba en el navegador, que es justo el viaje que el chip venía a ahorrar. Ahora el contador es un
botón, cada check fallado sale con su nombre y su workflow, y **Por qué** trae lo que imprimió ese
job.

Sale de la misma llamada que ya se hacía: el `statusCheckRollup` lleva `name`, `workflowName` y
`detailsUrl`, y el id del job está dentro de esa URL. Así que nombrar los fallos no cuesta ninguna
petición extra; sólo el log la cuesta, y por eso se pide y no se sondea.

Del log se quitan las dos columnas del runner (job y paso, iguales en todas las líneas) y la marca
de tiempo a la diezmillonésima; se guarda la cola y no la cabeza, porque una tanda de tests imprime
mil aciertos antes del fallo. Medido contra un job real: 200 líneas, 8.000 caracteres de cola, con
el paso que falló identificado (`Test remote control`).

Un check que no es un job de Actions —un CI externo informando un estado— no tiene log que leer
aquí, así que ofrece el enlace y nada más, en vez de un botón que no puede cumplir.

**H-15 — deshacer lo que hizo un run** (17/09/2026). Era la ficha de la Fase 1 que más pesaba, y
pesaba porque ya teníamos runs que escriben en la carpeta, un visor para ver qué hicieron y un commit
para quedarse con lo bueno — pero ninguna forma de volver.

Un punto de retorno es **un commit de git que no está en ninguna rama**, construido a través de un
índice temporal. Tomarlo no toca nada que el lector pueda ver: ni el árbol de trabajo, ni lo que
tenga en el índice, ni el stash, ni la rama. Un ref bajo `refs/flupcode/checkpoints/` impide que `git
gc` se lo lleve — medido: tras `gc --prune=now` el commit sigue ahí. Y respeta `.gitignore`, que es
lo que hace que un punto de un proyecto real sean unos kilobytes y no `node_modules` entero.

Restaurar es la mitad peligrosa y tiene dos reglas. **Dice qué ficheros escribiría y cuáles borraría
antes de tocar nada** — el plan se calcula grabando el presente igual que se graba un punto y
comparando los dos árboles, así que los ficheros que nadie añadió nunca a git salen también, que son
justo los que nadie espera perder. Y **graba el presente antes de empezar**, así que deshacer el
deshacer es el mismo botón en la fila que aparece arriba.

Verificado contra un repositorio real y por HTTP: tomar → plan (`write: [work.txt]`, `remove:
[junk.txt]`) → restaurar → el fichero vuelve, la basura se va, la rama sigue con un solo commit y el
índice del lector intacto. Y el camino de vuelta, con el punto de seguridad, devuelve exactamente el
estado anterior.

Y una que encontró el CI y no yo: `git commit-tree` **se niega a firmar** sin una identidad
configurada, así que en una máquina recién estrenada —o en el propio CI, que no tiene identidad
global mientras que la de un desarrollador sí— tomar un punto fallaba. Un punto lo firma ahora el
propio harness (`FlupCode <harness@flupcode.local>`), que además es más honesto: no es un commit del
lector, está en ninguna rama y no se empuja a ningún sitio.

Cerrado después: el punto guarda ahora el **resumen** de lo que concluyó la tarea (`summary`,
recortado) y la vista de Runs dibuja el **marcador** de cada punto bajo su tarea, con el resumen
plegable y un acceso a los puntos de retorno de la carpeta.

**H-16 — lo que costó** (17/09/2026). Se abarató sola: su dependencia era H-10 y la mitad del dato
ya estaba guardado. La tabla `tasks` tiene `tokens`, `cost`, `agent`, `model_json` y `attempt`, así
que el MVP del ticket —«timeline + coste»— era sobre todo sumar lo que ya había.

El dashboard de inicio cuenta tokens y **no ha mostrado nunca un precio**, ni un modelo, ni un
agente: se calcula en el navegador desde la lista de sesiones del motor, que sabe lo que gastó una
sesión y nada de por qué. Lo que sí sabe el harness es el porqué, porque lo escribió.

El número que no se podía ver de ninguna manera es **lo que se pagó dos veces**. Un reintento acotado
es una tarea nueva —eso era el diseño de H-22, para no borrar la evidencia del primer intento—, así
que el trabajo repetido se cobra repetido, y hasta ahora la segunda factura iba dentro de la primera.

Deliberadamente **sólo runs**, y lo dice en pantalla. El harness no ve un turno de chat normal, y
sumarle los totales de sesión del motor contaría cada tarea dos veces: una tarea *es* una sesión.
Mejor un número con dueño claro que dos que se solapan en silencio.

Un fallo que sólo se vio mirando la pantalla: el gráfico por día se escalaba con `Math.max(1, …)`, y
como el coste de un día es una fracción de dólar, el 1 ganaba y todas las barras salían al 3% de su
caja. La escala está ahora extraída y probada.

Cerrado después: el plugin de motor cronometra cada llamada (`tool.execute.before`/`after`), el
supervisor dibuja el **timeline de herramientas** por tarea, el Context Inspector muestra la
**latencia de MCP** por servidor, y el inicio dejó de descargar treinta transcripts para contar
mensajes: muestra los totales de `/harness/usage`.

**H-12 — qué está haciendo, y qué tocó** (17/09/2026). Las dos mitades que faltaban, y las dos
salieron más baratas de lo previsto por cosas que ya estaban.

**Archivos tocados**: no se le preguntan al motor ni se deducen de las llamadas a herramientas, se
sacan de los puntos de retorno que H-15 ya toma después de cada tarea. La diferencia entre un punto y
el anterior es exactamente lo que hizo esa tarea — **incluido un fichero escrito por un comando de
shell**, que ninguna lista de tool calls habría cazado. Hay prueba para ese caso justamente.

**Qué está haciendo**: la mitad de H-47 que la auditoría asigna a esta ficha. El harness sabe que una
tarea lleva dieciocho minutos; sólo el motor sabe que lleva dieciocho minutos dentro de un `glob`.
Ahora se pide al motor mientras alguien mira, y no se guarda: cambia cada segundo y en el registro de
eventos ahogaría todo lo demás.

**H-25 — el editor de permisos/policies** (18/09/2026). Cierra el ticket. La política del motor es
`permission: ask | allow | deny` para todo, o un mapa por herramienta, y el valor de una herramienta
puede a su vez ser un mapa de patrones (`bash: { "rm -rf *": "deny" }`), que es como se expresa la
precedencia. El formulario edita la acción plana de las claves que el motor nombra, y los mapas de
patrones se enseñan y se escriben de vuelta **intactos**: un formulario que los aplanara borraría
justo las reglas que más importan. Una clave sin valor no se escribe, así que quitar una regla la
quita de verdad. Los permisos concedidos con «permitir siempre» siguen aparte, porque son del runtime
y no de la política.

Lo único que queda fuera es mover agents y skills dentro del panel: se enlazan a sus pantallas, donde
se ve el fichero del que sale cada uno.

**H-20 — stage por hunk, descartar y mensaje generado** (18/09/2026). Cierra el ticket. El commit
era todo o nada por archivo, y el mensaje se escribía a mano. Ahora cada hunk del diff lleva su
casilla y su botón de descartar, y hay un botón para que el motor escriba el mensaje.

La parte delicada es reconstruir el parche: `git apply` no acepta «el hunk 3», acepta un parche, y
uno al que le falta un hunk o le sobra una línea de contexto se rechaza entero. `patch.ts` parte el
diff por sus cabeceras `@@` y lo vuelve a montar con la cabecera de fichero y sólo los hunks
elegidos, con una prueba que verifica que el resultado vuelve a leerse igual. En el servidor, un
commit con hunks los aplica al índice (`git apply --cached`) y luego confirma; los archivos sin
hunks se siguen añadiendo enteros, así que el flujo de siempre no cambia. Descartar un hunk es el
mismo parche al revés sobre el árbol de trabajo; descartar un archivo entero vuelve a lo que git
tiene, y borra el que git nunca vio.

El mensaje generado no gasta un turno de la conversación —que era justo lo que H-20 quitó—: el
servidor crea una sesión de usar y tirar, le pasa el diff seleccionado y recorta la respuesta. La
prueba comprueba que el diff truncado no se manda sin más y que un path que git ya no reporta no
llega a llamar al modelo.

**H-26 — las reglas de los menús, compartidas** (18/09/2026). Los dos composers eran dos copias, y la
del teléfono no tenía ni menú `/` ni `@` ni Enter para enviar. Las reglas de cuándo se abre un menú y
qué ofrece no dependen del tamaño de la pantalla, así que viven en `composer-menus` y los dos las
llaman: el menú `/`, el token `@`, el filtrado y el montaje de la mención son las mismas funciones
para ambos. El dibujo sí es distinto, y lo comparten a través de un `ComposerMenu` común que mantiene
las clases (`.fc-command-menu`, `.fc-command-item`) que ya usaba el escritorio.

Con eso, el composer del móvil gana Enter para enviar (con Shift+Enter para una línea nueva, como el
de escritorio), el botón de parar, los menús `/` y `@`, y una fila de delivery (steer/queue) en la
hoja de contexto. Y el menú `@` de ambos deja de ser solo de ficheros: ofrece también agentes y
artifacts, porque un agente es a lo que apunta el turno y un artifact es algo que la sesión ya
produjo.

**H-26 — un solo componente, y los context packs** (18/09/2026). Cierra el ticket. `Composer.tsx`
exporta ahora **un** componente con una variante (`desktop`/`mobile`); los dos trazados siguen
existiendo, pero comparten las reglas —qué abre un menú, qué es una mención, qué es un chat, el
micrófono— desde `composer-menus` y `composer-core`, así que un arreglo en uno llega al otro. La app
ya no elige entre dos componentes importados: pasa `variant` y el mismo juego de props.

Y `@pack` deja de ser un token decorativo. Un **context pack** es un conjunto con nombre de
referencias (`@archivo`, `@artifact`) guardado en el harness-server —tabla `context_packs`, global o
de una carpeta, un pack por nombre y carpeta—. El menú `@` los ofrece; elegir uno suelta sus
referencias en el borrador. Y el propio menú tiene «guardar esto como un pack» cuando el borrador ya
tiene menciones, que abre un diálogo de nombre y lo guarda. La capacidad viaja en `/harness/health`
(`packs`), así que un cliente nuevo contra un sidecar viejo no pregunta por la ruta.

**H-19 — el árbol, el visor y la búsqueda de archivos** (18/09/2026). El visor de diffs responde «qué
cambió»; faltaba «qué hay». La pantalla `/files` tiene el árbol a la izquierda y el archivo a la
derecha.

El árbol crece a un nivel por clic sobre el `fs.list` del motor (que lista hijos de un directorio) y
guarda lo cargado, así que cerrar y abrir una carpeta no vuelve a preguntar. El motor **lista** y
**busca** —`fs.find`, la misma búsqueda rankeada que ya usaba el menú `@`— pero no ofrecía leer texto:
su ruta de lectura devuelve bytes con un mime y lleva la ruta en la URL. Así que leer es del
harness-server: `GET /harness/files/read`, **confinado a la carpeta** (nada de `..`) y con tope de
512 KB, porque un visor no es una descarga. Un NUL en el primer bloque lo marca como binario y no se
devuelve como texto. La capacidad viaja en `/harness/health` (`files`).

Lo que queda fuera es «abrir en editor»: en una web no hay editor que abrir, y en el escritorio el
renderer está en sandbox; la ruta se ve y se copia a mano.

**H-27 — de dónde más salen las skills** (18/09/2026). Cierra el ticket. El catálogo ya contaba lo
que el motor tiene, lo que descarta y por qué; lo que faltaba era **instalar desde una carpeta o una
URL**. El motor lee además de sus carpetas lo que digan `skills.paths` y `skills.urls` en su
configuración, así que la pantalla de Skills tiene ahora una sección de fuentes: lista las que hay,
quita la que se pida y añade una carpeta o una URL. Escribir es un `PATCH /config` con las dos
listas, con `addSource`/`removeSource` en `skill-sources.ts` —trim, sin repetidos, y una lista vacía
nunca escribe basura— para que las reglas no vivan dentro del formulario.

La sección va **después** de los dos diagnósticos y **antes** de las cargadas: lo primero que
responde esta pantalla es «por qué no aparece la mía», y una skill traída de una URL no tiene fichero
en la máquina, así que si no se cuenta aquí acabaría en la lista de «ningún fichero de aquí lo
explica».

**H-31 — packs dentro de un run, y handoffs de verdad** (18/09/2026). Los packs existían desde H-26,
pero sólo llegaban a un prompt porque el composer los expandía a texto. Ahora un run puede llevar
**packs por nombre** (`packs` en el run, guardado con sus opciones), y el runner los resuelve una vez
para todas sus tareas: los refs que son ficheros del proyecto van como **`file` parts** —el motor los
lee con su propia herramienta Read, que es lo que significa «inyectar contexto»— y lo que no es un
fichero (un artifact, un agente) va como bloque de texto, porque no hay una parte que lo signifique.
Un ref con esquema, absoluto o con `..` nunca se abre: eso es de `packFiles`, con sus pruebas.

Y el handoff deja de ser «lo que la tarea anterior contestó». Al terminar cada tarea de agente, el
motor escribe una **nota de cierre** en una sesión aparte —Decidido, Rechazado, Riesgos, Ficheros,
Pendiente— que se guarda como Artifact `handoff` y es lo que recibe la siguiente. La respuesta cruda
es el respaldo si la nota no se puede escribir, así que no se pierde lo que la tarea dijo. Es
literalmente §6.2: un handoff, no un transcript.

Lo que queda fuera es elegir los packs desde el lanzador de workflows: hoy se pasan por la API del
run (`packs`), y un selector en la UI pide el editor de workflows de H-28.

**H-29 — un árbol por tarea, con merge y limpieza** (18/09/2026). Con `worktrees` en el run, cada
tarea de agente pide al motor un **worktree** propio (`/experimental/worktree`, que hace el `git
worktree add` sobre una rama `opencode/<slug>` bajo su directorio de datos) y escribe ahí. El slug
sale del nombre de la tarea, que trae espacios y no puede ser ni carpeta ni rama.

Lo importante no es crearlo, es que **todo lo de la tarea vaya en su árbol**. La sesión, el prompt,
la espera y la respuesta ya tomaban una carpeta; ahora toman la del worktree. Y lo que se deduce de
la carpeta también: la tarea `verify` comprueba el árbol de la tarea que está verificando —si no,
daría un veredicto sobre código que nadie tocó—, el checkpoint se toma en él y los findings se
anclan a sus rutas. `Checkpoint` ya llevaba su `directory`, así que el diff por tarea de
`filesPerTask` usa el de cada punto. La tarea guarda su `directory`, para que el panel pueda decir
dónde corrió.

El **merge es asistido**: `POST /harness/runs/:id/worktrees/merge` fusiona cada rama en el orden de
las tareas con `--no-ff` —un commit de merge deja el paso visible en el historial— y **aborta el
conflicto** en vez de dejar la carpeta a medias. La **limpieza** la hace el motor
(`removeWorktree`, que también borra la rama y su contabilidad de sandbox), desde el panel de runs.
Un run que no pide worktrees no crea ninguno, y la tarea lo comprueba.

Lo que queda fuera es pedirlo desde el lanzador: hoy el flag va en el run (`worktrees`), y un
selector pide el editor de workflows de H-28.

**H-30 — qué modelo usa cada rol, y cuándo parar a preguntar** (18/09/2026). Un run puede llevar una
`policy`: **modelo por rol**, **fallback** y **presupuesto**. «Rol» es el agente con el que corre la
tarea, porque es lo que un proceso dice sobre quién hace qué; una tarea que nombra su propio modelo
**gana** —la policy llena los huecos que deja un proceso, no corrige una decisión—. Las reglas viven
en `policy.ts`, funciones puras con sus pruebas: resolver el modelo, elegir el fallback y decir si el
presupuesto se alcanzó.

El **fallback** entra en el reintento: un reintento que repite el modelo que acaba de fallar está
haciendo la misma pregunta y esperando otra respuesta, así que si la policy nombra uno y no es el
mismo, se usa ese. El **presupuesto** se comprueba **entre tareas**, nunca a mitad de turno:
`finishTask` es donde existe por primera vez un recuento de tokens, y matar un turno para ahorrar
céntimos perdería el trabajo que estaba haciendo. Al alcanzarlo, el run queda `awaiting` con
`paused: "budget"`, la supervisión lo dice y el botón pasa a «continuar»; al continuar,
`budgetApproved` deja de comprobarlo, porque si no el mismo total lo volvería a pausar enseguida.

De paso, `taskFrom` ya parsea `model` en `POST /harness/runs`: lo tiraba, aunque `TaskInput` lo
llevaba.

Lo que queda fuera es elegir la policy desde el lanzador (hoy va en el run), que pide el editor de
H-28.

**H-35 — la conversación como fichero, y un enlace que no depende del motor** (18/09/2026). El
export eran doce líneas dentro de `app.tsx`: markdown, sin opciones y nada más. Ahora es
`export.ts`, funciones puras con pruebas —porque convertir un transcript en texto es justo lo que
pierde una parte en silencio— y las dos preguntas que de verdad se hacen tienen respuesta por
argumento: **con o sin el ruido de las herramientas** (razonamiento, llamadas, y la salida aparte,
que está apagada por defecto) y **markdown o los datos crudos** (JSON). Un diálogo de export recoge
las tres casillas y los dos formatos.

El **share** deja de ser sólo el host remoto del motor: el harness guarda una copia de la
conversación (`shared_conversations`) y la sirve en `/harness/shares/:id` como `text/markdown`, así
que el enlace lo hospeda FlupCode. La capacidad viaja en `/harness/health` (`shares`) y el botón
«copiar enlace» sólo aparece si el servidor sabe hacerlo.

Lo que queda fuera es una página de lectura propia para el enlace —hoy sirve el markdown tal cual— y
un índice de conversaciones compartidas, que nadie ha pedido todavía.

**H-37 — lo que el proyecto sabe, en cada turno** (18/09/2026). Notas por proyecto en el
harness-server (`project_memory`, una tabla con su carpeta, no la memoria del motor que es por sesión
y la elige el modelo): decisiones, convenciones, cosas aprendidas, escritas a mano desde el panel de
Memory, que tiene la sección «Project notes» encima de lo demás y con su caja para añadir.

Se entregan a cada turno de dos maneras, y el detalle importa. En un **run**, el runner las lee y las
pone delante del prompt de cada tarea, como ya hacía con los context packs (H-31): el harness compone
ese prompt, así que ahí el sitio es el prompt. En una **sesión interactiva**, el prompt lo compone el
motor y el harness sólo pasa el `system`, así que van ahí, junto al de Cowork o al de chat.

Una desviación que hay que decir: el ticket hablaba de `instructions[]`, que acepta rutas, y eso
obligaría a escribir en el `opencode.json` del proyecto —un fichero del lector, versionado— o a meter
las notas de todos los proyectos en la config global. Preferí no tocar su repositorio: el efecto para
quien lee es el mismo, y no deja un fichero que no pidió.

Lo que queda fuera es un sistema de memoria general —resúmenes automáticos, caducidad, confianza—,
que el audit descarta a propósito: esto es el bloc de notas del proyecto, no un cerebro.

**H-46 — la sesión que el motor ya no tiene** (18/09/2026). La sesión abierta se recuerda entre
recargas, pero el motor puede no tenerla: se borró, o es de otro motor que el que responde en esa
dirección ahora. Hasta aquí eso se veía igual que una sesión vacía —el transcript fallaba, el
compositor invitaba a escribir y cada turno habría dado 404— y encima el aviso de «no sigo al motor»
ofrecía un reintento que no podía funcionar nunca.

Lo que hacía falta era distinguir dos fallos que llegan igual de la red: la sesión no está
(`SessionNotFoundError`, con su `_tag`) o el motor no contesta. La primera se suelta: se olvida, se
limpia de `localStorage`, se dice con un aviso informativo y el lector vuelve al inicio. La segunda
se deja como estaba, con el aviso y el reintento de siempre, porque el transcript sigue en pantalla y
el motor puede volver. Antes de esto, `unwrap` tiraba un `Error` sin etiqueta y la app no podía
saber de cuál se trataba.

Lo que queda fuera es borrar la sesión del proyecto en el listado: si el motor no la tiene, no la
lista, así que no había nada que quitar.

**H-28 (parte 1) — el grafo, y lo que corre a la vez** (18/09/2026). Un run deja de ser una lista y
pasa a ser un grafo. Una tarea dice lo que espera con `dependsOn: [ids]`, o se sale del orden del
fichero con `parallel: true` — que se escribe como una lista vacía, para poder distinguirlo de «no
opino»—, y una tarea sin ninguna de las dos cosas sigue yendo después de la de arriba. Esa regla es
deliberada: un workflow v1 no cambia de comportamiento por haber añadido esto.

Todo lo que tiene las dependencias resueltas arranca a la vez, con un techo de cuatro tareas en vuelo
(el mismo número que pone el audit). El handoff cambia de forma: ya no es «lo que dijo la tarea
anterior» sino lo que concluyeron las dependencias, unidas, así que un `join` recibe las dos. El
directorio de un `verify` es el de la tarea que comprueba, también cuando son varias.

`when` es la válvula: `when: { task: check, is: [failed] }` hace que la tarea corra **solo** si el
chequeo falló. La tarea que nombra es dependencia aunque no se repita, porque la condición no se puede
contestar hasta que termina. Y si una tarea declara que espera ese fallo, el run no muere: llega a la
recuperación. La rama que esperaba un `success` se queda `skipped`, con el motivo escrito, en vez de
en cola para siempre.

Los reintentos conservan lo que H-22 decidió: son tareas nuevas. Ahora la segunda trae su propia
dependencia —el intento que la provocó— y el `verify` que la sigue espera al intento más nuevo, que es
lo que evita que un `verify#2` corra contra el `build#1` que ya había terminado. Los tests de siempre
(357 antes, 367 ahora) siguen pasando sin tocarlos, que era la condición para creerse el cambio.

Lo que falta de H-28: `foreach` (una tarea por elemento del plan, que necesita leer el plan), y el
**editor con grafo** —más los selectores de packs, worktrees y política en el lanzador, que esperan a
ese editor—. Van en la parte 3.

**H-28 (parte 2) — la timeline** (18/09/2026). El run se dibuja en un eje de tiempo dentro de su
tarjeta: una fila por cada conjunto de tareas que se solaparon, colocando cada barra por su `startedAt`
y su `finishedAt`. Lo que corrió a la vez se ve como dos filas, sin leer una sola marca de tiempo. Una
tarea que nunca arrancó —en cola, parada o `skipped` por el grafo— no tiene sitio en un eje de tiempo,
así que se nombra aparte en vez de dibujarse en el origen como si hubiera corrido.

La colocación es una función pura (`timelineLanes`) con sus tests: solapamiento a filas, reutilizar la
primera fila libre cuando una termina, y separar lo que no empezó. El eje sigue la dirección de
escritura (`inset-inline-start`), así que en RTL se lee de derecha a izquierda como el resto.

**H-28 (parte 3) — el editor con grafo** (18/09/2026). Un workflow es un fichero, así que el editor
edita el **texto**, no un formulario: si sólo se pudiera tocar lo que ya entiende, no se podría
introducir un `dependsOn`. Lo que se guarda lo valida el servidor leyéndolo otra vez —`saveWorkflow`
pasa por `parseWorkflow`— así que un fichero que no correría se rechaza en vez de guardarse. Una
edición no renombra el fichero: se reescribe el que estaba; lo que no existe se crea con un nombre
derivado del workflow. Y el sitio se elige: el proyecto (`.flupcode/workflows`, gana al global) o el
usuario (`~/.local/share/flupcode/workflows`).

Encima del texto, el **grafo**: columnas por profundidad de dependencia —una tarea un paso a la
derecha de lo último que espera, y lo que puede correr junto en la misma columna—, con líneas para las
dependencias. La colocación es otra función pura (`workflowGraph`) con sus tests, así que se prueba sin
navegador; el SVG sólo pinta lo que esa función decidió. El grafo dibuja lo que dice el fichero
guardado, no lo que se está tecleando: un borrador a medias no debería dibujar una forma que no
correría.

Al servidor le faltaba poder escribir workflows: H-21 los leía y los lanzaba, pero un fichero que no
se puede abrir ni guardar desde la app es un fichero que obliga a salir de ella. Ahora hay
`GET`/`PUT`/`DELETE /harness/workflows/:name`, y el panel cuelga del rail y de `/workflows`.

Lo que falta de H-28: `foreach` (una tarea por elemento del plan, que necesita leer el plan) y los
selectores de packs, worktrees y política en el lanzador, que van en la parte 4.

**H-28 (parte 4) — el lanzador** (18/09/2026). H-31, H-29 y H-30 cerraron cada uno diciendo lo mismo:
la API del run acepta packs, worktrees y política, y un selector en la UI pide el editor de H-28. Aquí
está el selector, y de paso arregla lo que el compositor no podía hacer: un workflow con más de un
input no cabía en una línea y se negaba a arrancar. Ahora abre un diálogo que pregunta **todos** los
inputs —el primero viene de lo que se escribió detrás del nombre— y no deja lanzar hasta que estén
contestados, en vez de arrancar con el resto vacíos.

En el mismo sitio van las tres decisiones del run: los packs (casillas, de los del proyecto), el flag
de un worktree por tarea que escribe, y una política mínima —modelo de reserva y presupuesto en tokens
o coste—. Todo opcional: lo que se deje en blanco no viaja, y el servidor recibe exactamente lo que el
lector pidió. El mismo diálogo se abre desde el botón Run del editor, para que los selectores existan
aunque el workflow tenga un solo input.

Lo que queda fuera de H-28 es sólo `foreach`: una tarea por elemento del plan exige decidir qué es un
elemento (el plan es markdown, y H-14 lo trata como texto), y esa decisión no está tomada todavía.

## 18. Arquitectura recomendada

```
┌──────────────────────────── renderer: packages/harness ─────────────────────────────┐
│ Rutas (/p/:project/s/:session, /run/:id) · Store por entidad (sessions, messages,     │
│ parts, runs, tasks, artifacts, checkpoints) con reductor de eventos · session-ui      │
│ (timeline, diff, composer) · Vistas: Supervisor, Artifacts, Context Inspector, Git,   │
│ Settings (editores) · transport.ts → HTTP/SSE local o túnel E2E                       │
└───────────────────────────────────────┬──────────────────────────────────────────────┘
                                        │ una sola base URL
┌───────────────────────────────────────▼──────────────────────────────────────────────┐
│ packages/harness-server (Bun, hospedado por harness-desktop main y `flupcode serve`) │
│  · SQLite propio: runs, tasks, workflows, artifacts, checkpoints, routines, policies, │
│    events (desnormalizados), pins/tags/stash                                          │
│  · Orquestador: ejecuta workflows (sesiones hijas legacy), gates, verify, watchdog,   │
│    reintentos, presupuestos, worktrees, checkpoints, handoffs, reanudación            │
│  · Cron de rutinas · git (commit/branch/PR) · escritura de ficheros de config/agents  │
│  · Proxy autenticado al motor (contraseña generada) + allowlist para remoto           │
│  · API HTTP + SSE propia (runs/tasks/artifacts) y passthrough del /event del motor    │
└──────────┬──────────────────────────────────────────────────────┬────────────────────┘
           │ SDK legacy (+ v2 events cuando aplique)               │ hooks in-loop
┌──────────▼──────────────────┐                     ┌─────────────▼─────────────────────┐
│ opencode serve (read-only)  │ ◀── carga ────────  │ @flupcode/engine-plugin            │
│ runtime legacy + v2, tools, │                     │ system-prompt capture, timing de   │
│ MCP, LSP, permisos, snap.   │                     │ tools, permission.ask policy,      │
└─────────────────────────────┘                     │ tools propias: artifact.write,     │
                                                    │ handoff.write, verify.report       │
                                                    └───────────────────────────────────┘
```

Decisiones clave:

- **Un proceso de harness fuera del navegador es obligatorio.** Hospedarlo en el main de Electron y en `flupcode serve` (evolución natural de `flupcode remote`); el renderer habla con él, y él con el motor. El túnel remoto apunta al harness-server, que aplica la allowlist.
- **Upstream sigue read-only.** Todo lo que necesite estar "dentro del loop" va en un plugin de motor (ya hay precedente con el de variantes): captura del system prompt, timing de tools, política de permisos, tools propias para que los agentes registren artefactos y handoffs.
- **Legacy ahora, V2 después.** El motor V2 es el futuro de OpenCode, pero hoy no ejecuta lo que un harness necesita. Aislar la elección detrás de `EngineAdapter` y seguir el checklist de `core/src/session/runner/llm.ts` para migrar tarea a tarea (los eventos durables con replay son la primera capacidad V2 que conviene aprovechar).
- **Reutilizar `session-ui`/`ui`** para todo lo que sea renderizado de conversación y diffs; invertir el tiempo del equipo en Run/Task/Workflow, supervisión, verificación y contexto, que es donde no hay nada que reutilizar.
- **Estado del renderer**: stores normalizados por id, reductor único de eventos, sin refetch salvo reconciliación; rutas reales.
- **Datos**: lo del motor en el motor (sesiones, mensajes, permisos, config); lo del harness en su SQLite; en el navegador sólo preferencias de vista.

## 20. Respuestas a las preguntas estratégicas

**Si FlupCode consigue paridad con OpenCode, ¿qué debe construir después para ser una categoría superior?** El **Run**: la ejecución durable, observable y gobernada de un objetivo por uno o varios agentes. Es lo que hoy nadie ofrece con GUI y móvil: OpenCode se detiene en la sesión; la app oficial la enseña; Claude Code lo hace en terminal y de forma opaca; Cursor/Codex lo llevan a la nube sin proceso ni gates; OMC lo simula con prompts y hooks. Concretamente: workflows declarativos con gate humano y gate de verificación con evidencia (H-21/H-22), supervisión por tarea con steer/retry/cancel (H-12), artefactos y checkpoints (H-14/H-15), Context Inspector y packs (H-17/H-31), policies de permisos/modelo/presupuesto (H-04/H-30), y todo ello operable desde el teléfono con el canal remoto que ya existe. La app oficial de OpenCode nunca hará esto porque OpenCode se define como runtime; ahí está el hueco.

**¿Cuál es el conjunto mínimo de primitivas para ser un verdadero Agent Harness?** Seis nuevas, propiedad del harness: **Run/Task** (ejecución con estado sobre sesiones del motor), **Workflow** (grafo declarativo de tareas con gates), **Artifact** (salida persistente y referenciable), **Checkpoint** (snapshot + resumen restaurable), **Policy** (permisos + modelo + presupuesto aplicables sin tocar la configuración del proyecto) y **Context Pack** (contexto reutilizable inyectable, con handoffs como caso particular). Y cinco del motor que sólo hay que exponer y editar: **Agent, Session, Skill, Tool (incl. MCP), Model, Permission**. Con eso se construyen feature development, bug fix, refactor, review, security audit, tests, docs, migration, research y architecture analysis como configuración, no como código. Agent Team no es primitiva; es un Run visto por agente.

**¿Qué construir en los próximos 3–6 meses?** En orden: corregir el runtime y el estado (Fase 0), crear el harness-server con Run/Task, supervisión, artefactos, checkpoints, observabilidad y Context Inspector (Fase 1), y entregar workflows con verificación, review en diff y git (Fase 2). Si sobran semanas, paralelismo con worktrees y policies de modelo (Fase 3). No añadir ninguna feature aislada que no se apoye en estas primitivas.
